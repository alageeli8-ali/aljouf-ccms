# 15 — سجل القرارات الفنية (ADR)

كل قرار بصيغة: السياق، القرار، البدائل، العواقب. الحالة: مقترح (بانتظار اعتماد المكتب) / معتمد / مستبدل.

## ADR-001 Modular Monolith

- **الحالة:** مقترح
- **السياق:** نظام متوسط الحجم (NFR-PRF-04)، فريق صغير يصونه، معاملات تمتد عبر عدة وحدات (الاعتماد)، ومتطلب صريح بفصل الوحدات وجعل الاختيارية مستقلة.
- **القرار:** تطبيق واحد قابل للنشر بوحدات أعمال مفصولة منطقيًا: مشروع عقود ومشروع داخلي لكل وحدة، ومخطط مستقل في القاعدة، وحدود مفروضة باختبارات معمارية.
- **البدائل:** خدمات مصغرة (رُفض: كلفة تشغيل وتعقيد معاملات موزعة دون حاجة حجمية)؛ تطبيق طبقي تقليدي دون حدود وحدات (رُفض: يصعّب فصل الوحدات الاختيارية والصيانة).
- **العواقب:** نشر وتشغيل بسيطان؛ إمكانية استخراج وحدة (AI أولًا) كخدمة لاحقًا لأن التواصل عبر العقود والأحداث.

## ADR-002 ASP.NET Core على .NET 10 LTS

- **الحالة:** مقترح
- **السياق:** التقنية محددة من المكتب (ASP.NET Core/C#). إصدار .NET 8 LTS ينتهي دعمه في نوفمبر 2026.
- **القرار:** .NET 10 LTS مع Minimal APIs مجمعة لكل وحدة.
- **البدائل:** .NET 8 (رُفض: نهاية الدعم قريبة)؛ Controllers (مقبول لكن Minimal APIs أخف وأوضح لتجميع الوحدة).
- **العواقب:** دعم حتى نوفمبر 2028؛ خطة ترقية إلى LTS التالي ضمن الصيانة.

## ADR-003 PostgreSQL بدل SQL Server

- **الحالة:** مقترح — يُعاد النظر إن أفاد المكتب بترخيص SQL Server قائم وخبرة تشغيلية فيه (Q-05)
- **السياق:** المطلوب قاعدة واحدة من الاثنتين بعد تقييم البيئة والتراخيص والتكاملات. بيئة المكتب Microsoft 365 للهوية والبريد، ولا يظهر ارتباط بقاعدة SQL Server بعينها. الإصدار 0.5 على PostgreSQL.
- **التقييم:**

| المعيار | PostgreSQL 16+ | SQL Server 2022 |
|---|---|---|
| الترخيص | مفتوح المصدر، بلا كلفة | Standard/Enterprise بترخيص أنوية؛ Express محدود (10 GB) لا يصلح للإنتاج |
| النشر داخل المركز وفي الحاويات | ممتاز على Linux | مدعوم على Linux وحاويات |
| EF Core | Npgsql ناضج | ممتاز (المزود الأصلي) |
| البحث النصي العربي | FTS + `pg_trgm` + تطبيع في التطبيق | Full-Text مع مقسّم كلمات عربي |
| متجهات للذكاء الاصطناعي | `pgvector` ناضج داخل القاعدة نفسها | دعم المتجهات حديث في الإصدارات الأحدث |
| JSON للسياسات واللقطات | `jsonb` مفهرس | JSON نصي مع دوال |
| التوافق مع الإصدار 0.5 | مباشر | يتطلب تحويلًا |
| خبرة التشغيل المتوقعة في فريق Microsoft | تحتاج تأهيلًا بسيطًا | مألوفة غالبًا |

- **القرار:** PostgreSQL 16 أو أحدث.
- **العواقب:** لا كلفة ترخيص؛ متجهات الذكاء الاصطناعي داخل القاعدة نفسها (قاعدة واحدة كما هو مطلوب)؛ تحتاج نسخ احتياطي ومراقبة مناسبة لـ PostgreSQL. الشيفرة عبر EF Core تبقي التحول إلى SQL Server ممكنًا بكلفة متوسطة (البحث والمتجهات و`jsonb` هي نقاط الاختلاف).

## ADR-004 الدخول بـ Entra ID بنمط BFF

- **الحالة:** مقترح
- **السياق:** هوية المكتب في Microsoft 365؛ البيانات مصنفة؛ المطلوب أقل سطح هجوم.
- **القرار:** OIDC Authorization Code + PKCE في الخادم، وجلسة كعكة HttpOnly؛ الواجهة والـ API من الأصل نفسه؛ لا رموز في المتصفح. الأعضاء الخارجيون حسابات ضيوف B2B.
- **البدائل:** SPA مع MSAL.js ورموز في المتصفح (رُفض: رموز معرضة لـ XSS)؛ حسابات محلية (رُفض: تكرار الهوية وضعف التحقق الثنائي).
- **العواقب:** CSRF مطلوبة؛ الجلسات في القاعدة لتعدد النسخ.

## ADR-005 الوحدات الاختيارية مسجلة دائمًا ومحجوبة بالمفاتيح

- **الحالة:** مقترح
- **السياق:** التعطيل يجب ألا يفقد بيانات، والتفعيل يجب ألا يتطلب ترحيلًا.
- **القرار:** جداول وترحيلات الوحدات الاختيارية موجودة دائمًا؛ التفعيل والتعطيل على مستوى نقاط النهاية والمهام والمنافذ عبر `IFeatureGate`؛ الوحدات الأساسية تعرّف منافذ لها تنفيذ افتراضي دائم.
- **البدائل:** تحميل الوحدات ديناميكيًا كإضافات (رُفض: تعقيد النشر والاختبار)؛ إصدارات منفصلة بالوحدة وبدونها (رُفض: لا يُبدَّل من لوحة الإدارة).
- **العواقب:** حجم الصورة يشمل كل الوحدات؛ مصفوفة اختبار المفاتيح إلزامية (TS-20).

## ADR-006 الإقرار الداخلي في الوحدة الأساسية والتوقيع الإلكتروني في وحدة اختيارية

- **الحالة:** مقترح
- **السياق:** بعض اللجان تشترط توقيع الحاضرين قبل اعتماد الرئيس، والمتطلب أن يعمل النظام دون التوقيع الإلكتروني.
- **القرار:** «إقرار المحضر» قدرة أساسية بثلاث طرق (09 §1)؛ التوقيع ذو الحجية يُضاف عبر SIG كطريقة ثالثة. MIN تملك حالة الإقرار؛ SIG تملك تفاصيل التشفير والمزوّد.
- **العواقب:** اللجان التي تشترط الإقرار تعمل من اليوم الأول؛ تعطيل SIG لا يُعلق محضرًا.

## ADR-007 React + Ant Design بإعداد RTL

- **الحالة:** مقترح
- **السياق:** واجهة إدارية كثيفة البيانات (جداول، نماذج، تواريخ) بالعربية أولًا.
- **القرار:** React 19 + TypeScript + Vite، وAnt Design 5 (دعم RTL ومحلية عربية مدمجان، ومكونات جداول ونماذج ناضجة)، بهوية بصرية للمكتب عبر رموز التصميم.
- **البدائل:** MUI (يتطلب إعداد RTL إضافي)؛ مكونات مخصصة بالكامل (كلفة عالية)؛ نظام تصميم منصات هيئة الحكومة الرقمية — يُعتمد إن ألزم المكتب به للأنظمة الداخلية (Q-14).
- **العواقب:** اتساق سريع؛ تخصيص الهوية عبر الرموز.

## ADR-008 التواصل بين الوحدات: عقود + Outbox، ومخطط لكل وحدة

- **الحالة:** مقترح
- **القرار:** الاستعلامات والأوامر المتزامنة عبر واجهات `*.Contracts`؛ ردود الفعل عبر أحداث تكامل في صندوق صادر داخل المعاملة؛ لا كتابة في مخطط وحدة أخرى؛ مفاتيح أجنبية عابرة للمخططات نحو `iam.users` و`org.org_units` فقط.
- **العواقب:** سلامة المراجع الأخرى مسؤولية التطبيق (تُختبر)؛ إمكانية فصل الوحدات لاحقًا.

## ADR-009 النشر بالحاويات داخل المملكة

- **الحالة:** مقترح
- **القرار:** صور OCI، وDocker Compose للبداية على خادم أو اثنين، وقابلية الانتقال إلى Kubernetes أو منصة حاويات معتمدة دون تغيير الصور. Nginx وكيلًا عكسيًا.
- **العواقب:** لا اعتماد على خدمات سحابية مملوكة؛ دليل تشغيل مطلوب.

## ADR-010 Quartz.NET للمهام المجدولة

- **الحالة:** مقترح
- **القرار:** Quartz.NET (ترخيص Apache 2.0) بمخزن مهام PostgreSQL ووضع cluster.
- **البدائل:** Hangfire (مقبول؛ مخزن PostgreSQL من المجتمع)؛ cron على الخادم (رُفض: خارج التطبيق، بلا تنسيق بين النسخ، كما في الإصدار 0.5).
- **العواقب:** المهام جزء من التطبيق ومراقبة من صفحة الصحة.

## ADR-011 PDF عبر Chromium من قالب HTML

- **الحالة:** مقترح
- **السياق:** المحاضر الرسمية بالعربية تتطلب تشكيلًا واتجاهًا صحيحين وترويسة المكتب.
- **القرار:** قوالب HTML/CSS تُحوَّل بـ Playwright/Chromium داخل حاوية العامل.
- **البدائل:** مكتبات PDF برمجية (تشكيل العربية فيها أضعف وبعضها تجاري الترخيص).
- **العواقب:** حاوية العامل أكبر وتحتاج ذاكرة أعلى (03 §8.1)؛ القوالب يحررها مصمم الواجهة.

## ADR-012 إعادة البناء بدل تطوير الإصدار 0.5

- **الحالة:** مقترح
- **السياق:** الإصدار 0.5 (Python/FastAPI، واجهة JavaScript بلا بناء) أثبت قواعد العمل، لكن المكتب حدد React/TypeScript وASP.NET Core، والنطاق الجديد أوسع (النصاب، التصويت، التمرير، التصعيد، الوحدات الاختيارية، ثنائية اللغة).
- **القرار:** بناء جديد يحمل قواعد 0.5 (00 §4)، مع سكربت ترحيل إن استُخدم 0.5 ببيانات حقيقية.
- **العواقب:** يبقى 0.5 للعرض والتدريب حتى إطلاق النظام الجديد؛ لا يُطور بميزات جديدة.

## ADR-013 البحث داخل PostgreSQL

- **الحالة:** مقترح
- **القرار:** FTS + `pg_trgm` على جدول فهرس موحد يحمل `body_id` والتصنيف، مع تطبيع عربي في التطبيق؛ البحث الدلالي إضافة من AI.
- **البدائل:** OpenSearch/Elasticsearch (رُفض الآن: مكون إضافي للتشغيل وتكرار للصلاحيات؛ يُعاد النظر إن لم يتحقق NFR-PRF-02 مع نمو البيانات).
- **العواقب:** مكون أقل؛ مرشّح الصلاحيات في الاستعلام نفسه.

## ADR-014 OpenAPI مولّد من الشيفرة وعميل TypeScript مولّد

- **الحالة:** مقترح
- **القرار:** الشيفرة مصدر العقد؛ يُولَّد OpenAPI 3.1 في البناء، ويُفحص الفرق الكاسر في كل طلب دمج، ويُولَّد عميل الواجهة منه.
- **العواقب:** لا انحراف بين الواجهة والخلفية؛ Swagger UI متاح في غير الإنتاج فقط.

## ADR-015 بناء دون اتصال بـ NuGet: موصل PostgreSQL مصغّر للتطوير، وNpgsql للإنتاج

- **الحالة:** معتمد للمرحلة 1 — يُراجع عند توفر الوصول إلى NuGet في بيئة البناء
- **السياق:** بيئة البناء في المرحلة 1 تحجب مستودع حزم NuGet (api.nuget.org) بسياسة الشبكة، بينما يتوفر ‎.NET 10 SDK من مستودع Ubuntu وnpm وPostgreSQL 16. حزم Npgsql وEF Core وMicrosoft.AspNetCore.OpenApi وOpenIdConnect وxUnit كلها من NuGet.
- **القرار:**
  1. طبقة البيانات تعتمد على واجهة ADO.NET القياسية `DbDataSource` فقط (`Ccms.BuildingBlocks.Data`).
  2. بناء الإنتاج: `-p:UseNpgsql=true` يربط Npgsql الرسمي (`NpgsqlDataSource` يرث `DbDataSource`) — سطر واحد في `DataSources.Create`.
  3. بناء التطوير والاختبار دون اتصال: `Ccms.Data.PgWire` موصل مصغّر بالبروتوكول الرسمي لـ PostgreSQL (SCRAM-SHA-256، معاملات نصية، معاملات قاعدة بيانات). **يرفض التطبيق الإقلاع في الإنتاج إن بُني به** (NFR-SEC-12).
  4. وثيقة OpenAPI 3.1 تُولّد من مستكشف الواجهات المدمج (ApiExplorer) ومصدّر JSON Schema في System.Text.Json، وتُعرض بواجهة Swagger UI من حزمة npm.
  5. الدخول الموحد OIDC (PKCE + RS256 + nonce) منفذ بمكتبات التشفير المدمجة، ومختبر على مزوّد هوية وهمي.
  6. الاختبارات: مشغّل تكامل طرف لطرف يشغّل التطبيق الحقيقي كعملية مستقلة على PostgreSQL حقيقي.
- **البدائل:** إيقاف العمل حتى يُتاح NuGet (رُفض: يؤخر التسليم دون داعٍ)؛ تغيير التقنية (رُفض: مخالف للتقنيات المعتمدة).
- **العواقب:** الصورة الإنتاجية تُبنى في خط تكامل له وصول إلى NuGet (Dockerfile جاهز). عند توفر NuGet يُستحسن: نقل الاختبارات إلى xUnit (الاختبارات مكتوبة بأسلوب قابل للنقل المباشر)، واستبدال المولّد المحلي بـ Microsoft.AspNetCore.OpenApi، واستبدال تنفيذ OIDC بـ Microsoft.AspNetCore.Authentication.OpenIdConnect، وإبقاء الموصل المصغّر للتطوير المحلي فقط أو حذفه.

## ADR-016 الوصول للبيانات بـ SQL صريح وترحيلات SQL مرقّمة بدل EF Core

- **الحالة:** معتمد — يعدّل ADR-003 وجدول 03 §10 في بند «الوصول للبيانات» و«ترحيلات لكل وحدة»
- **السياق:** EF Core غير متاح دون NuGet (ADR-015)، والمكتب يحتاج ترحيلات قابلة للمراجعة من مسؤول قاعدة البيانات قبل تطبيقها في الإنتاج، وقيود تكامل لا يعبّر عنها EF Core بسهولة (مشغلات سلسلة التدقيق، فهارس جزئية، منع التعديل على جداول الإلحاق).
- **القرار:** كل وحدة تكتب SQL صريحًا بمعاملات مسماة عبر `ISql`؛ الترحيلات ملفات `db/migrations/V###__name.sql` يطبقها `MigrationRunner` بحساب المالك في معاملة لكل ملف، مع قفل استشاري، وبصمة SHA-256 تمنع تعديل ترحيل مطبق.
- **البدائل:** EF Core Migrations (مؤجل؛ يمكن إضافته لاحقًا لوحدات جديدة إن رأى الفريق ذلك، مع إبقاء ملفات SQL مصدر الحقيقة).
- **العواقب:** أداء واستعلامات واضحة وقابلة للمراجعة؛ تكرار بعض كود التعيين يدويًا؛ تغطية الاختبارات تشمل كل استعلام عبر HTTP.

## ADR-017 السجل التاريخي بالإنهاء والإنشاء، والخط الزمني من سجل التدقيق

- **الحالة:** معتمد (المرحلة 2)
- **السياق:** المطلوب الاحتفاظ بتاريخ كامل للعضويات والمدد والسياسات دون حذف البيانات الرسمية، وعرض خط زمني لنشاط الجهة والاجتماع.
- **القرار:**
  1. التغيير الجوهري في العضوية (الصفة، الرئاسة) يُنهي السجل القائم (`status = ended` مع `end_date` و`end_reason` و`ended_by`) ويُنشئ سجلًا جديدًا يشير إليه السجل القديم (`replaced_by_member_id`). لا يُعدّل السجل المنتهي.
  2. المدد (`bodies.body_terms`) وفحوص النصاب (`meetings.quorum_checks`) جداول إلحاقية بلا UPDATE/DELETE لحساب التطبيق، والسياسات بإصدارات تُثبَّت على الاجتماع عند جدولته.
  3. البند المؤجل لا يُنقل بل يُنسخ إلى الاجتماع اللاحق بمرجع أصله (`carried_from_item_id`)، ويبقى الأصل بحالة «مؤجل» وسببه.
  4. الخط الزمني يُقرأ من `audit.audit_events` عبر عقد `IActivityQuery` بدل جداول أحداث منفصلة.
- **البدائل:** جداول تاريخ منفصلة بمشغلات (رُفض: تكرار مع سجل التدقيق)؛ التعديل في المكان مع سجل تغييرات (رُفض: يصعّب استعلام «الأعضاء في تاريخ معين»).
- **العواقب:** استعلامات «الساري في تاريخ» بسيطة (`start_date ≤ d ≤ end_date`)؛ عضوية المستخدم في الجهة قد تتعدد سجلاتها، ويُعتد بالأحدث عند تداخلها في اليوم نفسه.

## ADR-018 دورة اعتماد المحضر قابلة للتهيئة لكل جهة، والتعديل بعد الاعتماد بإصدار جديد، ومنع التكرار بمفتاح الطلب، وPDF عربي دون مكتبات

- **الحالة:** معتمد (المرحلة 3)
- **السياق:** المكتب طلب ألا يفرض النظام توقيعًا أو موافقة موحدة على كل اللجان، وأن يعمل مسار اعتماد بديل حين تكون وحدة التوقيع معطلة مع توثيق من اعتمد وكيف، وألا يُعدَّل محضر معتمد بصمت، وألا يتكرر القرار بإعادة المحاولة. ومكتبات PDF غير متاحة دون NuGet (ADR-015).
- **القرار:**
  1. دورة الاعتماد جزء من سياسة الجهة بإصداراتها (`minutes_workflow`): كل مرحلة مراجعة اختيارية، والتوقيع `none` أو بأحد ثلاثة نطاقات، والاعتماد النهائي إما من الرئيس داخل النظام أو اعتماد صاحب صلاحية خارج النظام يسجله أمين السر بمرجع ومستند. تُثبَّت لقطة الدورة في المحضر عند إنشائه.
  2. طريقة التوقيع تُحدد وقت طلبه عبر عقد `ISignatureGateway`: إن لم تكن البوابة جاهزة (التوقيع معطل، أو مفعّل دون ربط مزوّد — المرحلة 6) يُستخدم البديل في السياسة (إقرار إلكتروني داخل النظام أو توقيع ورقي مرفوع) ويُحفظ السبب مع كل طلب توقيع.
  3. التعديل بعد الاعتماد على سجل المحضر نفسه: يُفتح بسبب، فتُنشأ إصدارات جديدة تمر بالدورة كاملة أو بالاعتماد النهائي فقط حسب السياسة؛ الإصدار المعتمد السابق وقراراته وأرقامها لا تتغير، والقرار الجديد يعدّل السابق أو يلغيه بربط صريح. (بدل «محضر تصحيح» منفصل في 08 §2.5: يبقى للاجتماع محضر واحد بسجل إصدارات واحد.)
  4. منع التكرار: مرشّح عام على نقاط الإنشاء يحفظ (المستخدم، المفتاح، المسار، بصمة الطلب، الرد) ويعيد الرد الأول؛ إضافة إلى قيود القاعدة (مشاركة واحدة لكل عضو في التصويت، ومقترح مفتوح واحد لكل قرار، وإصدار القرارات من حالة «مقترح» فقط داخل معاملة الاعتماد).
  5. PDF: مولّد داخلي في `Ccms.BuildingBlocks/Pdf` بتشكيل عربي (Presentation Forms-B ولام ألف)، وترتيب ثنائي الاتجاه مبسط، وخطوط Noto Sans/Noto Sans Arabic (SIL OFL) مقتطعة ومضمنة مع خريطة ToUnicode. نسخة الإصدار المعتمد تُحفظ مستندًا ببصمتها ورمز تحقق.
- **البدائل:** QuestPDF أو iText (غير متاحة دون NuGet، وiText برخصة AGPL)؛ توليد PDF بمتصفح بلا واجهة (يضيف اعتمادًا ثقيلًا في الخادم).
- **العواقب:** النظام يعمل كاملًا والتوقيع والذكاء الاصطناعي معطلان؛ التشكيل الحركي (التشكيل بالحركات) لا يُرسم في PDF؛ رمز QR غير مضمن بعد (رمز تحقق نصي).

## ADR-019 دورة مهام قابلة للتهيئة بضوابط ثابتة، و«متأخرة» حالة محسوبة، والتصعيد في سياسة الجهة، والبوابة الخارجية مقيدة من الخادم، ولا ادعاء لإرسال الخطاب

- **الحالة:** معتمد (المرحلة 4)
- **السياق:** المطلوب أن تكون حالات المهام وصلاحياتها قابلة للتهيئة، وألا يُعد رفع الملف اكتمالًا، وأن يُفصل المنفذ عن المتابع، وأن تكون مستويات التصعيد قابلة للتهيئة ويُسجل كل تصعيد ومستلمه، وأن تكون بوابة الجهات اختيارية لا يتعطل بتعطيلها العمل الداخلي، وألا يُدّعى إرسال خطاب رسمي دون تكامل معتمد.
- **القرار:**
  1. الحالات والانتقالات في جدولين (`tasks.workflow_statuses` و`tasks.workflow_transitions`) لكل انتقال صلاحيته وأطرافه واشتراط السبب؛ ويطبق محرك المهام **ضوابط ثابتة لا تُهيأ**: الوصول إلى المراجعة والإكمال لا يتم إلا بالإجراءات الأساسية (الرفع بمخرجاته، والتحقق بقبول المخرجات، والإقرار الذاتي حين لا يلزم تحقق)، والتحقق ممنوع على المنفذ وممثل الجهة ومدير الإدارة المنفذة، والإجراءات الأساسية لا تُعطّل.
  2. «متأخرة» حالة محسوبة (فئة `derived`) من الموعد والحالة المفتوحة، لا تُخزن في المهمة؛ فتبقى الحالة الفعلية معروفة، ولا يحتاج التأخر إلى عامل يغير الحالات.
  3. التصعيد قاعدة ضمن إصدار سياسة الجهة (`escalation_rule`)؛ عامل خلفي يقيّمها ويسجل في `tasks.escalations` الإلحاقي سجلًا واحدًا لكل (مهمة، نوع، مستوى، فترة) بقائمة مستلميه، ويُقر كل مستلم بالاطلاع.
  4. البوابة: نفس التطبيق ونفس الحسابات المحلية، لكن صلاحيات ممثل الجهة منفصلة (`TaskSets` داخلية/بوابة) ولا تُمنح إلا والبوابة مفعلة وكلمة المرور غير مؤقتة، والدخول نفسه يُرفض عند التعطيل؛ ومسارات `/portal/*` تعيد نموذجًا مقتصرًا لا يتضمن الوصف الداخلي ولا ما لم يُشارك. المستند يُرى خارجيًا فقط بعلامة `external_visible` على ربطه بالمهمة.
  5. عند تعطيل البوابة يسجل مسؤول المتابعة ما يرد من الجهة كتحديث «مسجّل» بقناته الرسمية ومرجعه، ويمر بالمحرك نفسه.
  6. الخطاب يمر بمسودة ← معتمد (من غير المعد) ← مُرسل؛ و«مُرسل» يتطلب في القاعدة رقم صادر وتاريخًا (يدوي) أو مرجع تكامل؛ والإرسال الآلي عبر عقد `ICorrespondenceGateway` الذي يعلن جاهزيته، والموصل الحالي غير جاهز دائمًا لعدم توثيق واجهة «قمم».
- **البدائل:** محرك سير عمل عام (BPMN) — مؤجل لحجمه وصعوبة ضبط الضوابط؛ بوابة كتطبيق منفصل بقاعدة منفصلة — يضاعف التشغيل والمزامنة دون حاجة حالية؛ تخزين «متأخرة» كحالة — يفقد الحالة الفعلية ويحتاج عكسًا عند التمديد.
- **العواقب:** المكتب يضيف حالات انتظار أو تنفيذ ويغيّر الصلاحيات والأطراف دون كسر قواعد الإغلاق؛ والبوابة يمكن فصلها مستقبلًا خلف وكيل عكسي في المنطقة المحايدة دون تغيير النموذج.

## ADR-020 التوقيع الإلكتروني وحدة اختيارية مستقلة بثلاثة أنواع منفصلة، وتعطيل لا يغيّر الحالة، وتشفير PDF منفذ داخليًا

- **الحالة:** معتمد (وحدة التوقيع الإلكتروني)
- **السياق:** المطلوب وحدة توقيع تُفعّل وتُعطّل دون أن تتوقف إدارة المحاضر، وثلاثة أنواع لا يُخلط بينها، وواجهة مزوّد قابلة للاستبدال، وربط كل طلب بإصدار ثابت وبصمته، وألا يُدّعى اعتماد نظامي قبل التكامل الفعلي. ولا يوجد مزوّد معتمد متعاقد معه (Q-09)، والبناء دون اتصال بـ NuGet (ADR-015) فلا تتوفر مكتبة توقيع PDF ولا مرجع `System.Security.Cryptography.Pkcs`.
- **القرار:**
  1. مشروع ومخطط مستقلان (`sig`) يستبدلان تنفيذ `ISignatureGateway` الافتراضي عند تحميلهما؛ والمحاضر تستقبل النتائج عبر `IMinutesSignatureSink`. سياسة الجهة تقرر وجود مرحلة توقيع، والوحدة تقرر الموقّعين وترتيبهم ونوعهم.
  2. ثلاثة أنواع منفصلة بأسماء صريحة؛ «الموافقة الموثقة» توسم دائمًا بأنها ليست توقيعًا رقميًا، ونتيجة التحقق تميّز السلسلة الموثوقة من الاختبارية وغير الموثوقة.
  3. طلب واحد لكل إصدار، بلقطة من الإعدادات والمسار، ونسخة PDF لا تُستبدل؛ والتعديل يُبطل الطلب بسبب ويبدأ طلبًا جديدًا على الإصدار الجديد.
  4. التعطيل يمنع الجديد ولا يغيّر حالة أي طلب؛ الطلبات الجارية تُعالج بإجراء صريح مسجل (تعليق أو تحويل للبديل)، واستدعاءات المزوّد أثناءه تُحفظ مؤجلة.
  5. توقيع CMS/CAdES منفصل يُكتب بـ `AsnWriter`، ويُضمَّن في PDF بتحديث تزايدي لكل موقّع، مع متحقق داخلي؛ ومزوّد تجريبي بجهة إصدار اختبارية للاختبار فقط، ممنوع في الإنتاج.
- **البدائل:** مكتبة توقيع PDF تجارية أو مفتوحة — غير متاحة دون اتصال، وتُراجع عند التعاقد؛ اعتبار الموافقة داخل النظام «توقيعًا إلكترونيًا» — مرفوض لأنه يضلل بشأن الحجية؛ إلغاء الطلبات الجارية آليًا عند التعطيل — مرفوض صراحة في المتطلبات.
- **العواقب:** إضافة مزوّد معتمد = تنفيذ `ISignatureProvider` وضبط جذور الثقة دون تغيير المحاضر؛ والتشفير الداخلي يحتاج مراجعة أمنية مستقلة قبل الإنتاج، ويبقى بلا ختم زمني ولا فحص إلغاء حتى يتوفر المزوّد.

## ADR-021 الذكاء الاصطناعي وحدة اختيارية تكتب في مخططها فقط، ومخرجاتها مسودات مسندة يتحقق منها الخادم، وبيانات المكتب لا تُرسل إلا وفق التصنيف

- **الحالة:** معتمد (وحدة الذكاء الاصطناعي)
- **السياق:** المطلوب وحدة تُفعّل وتُعطّل دون إعادة بناء، بعشر وظائف ومزوّد قابل للتبديل، وألا ترسل بيانات مصنفة دون تصريح، وأن تكون مخرجاتها مسودات بمراجع لا تختلق، وألا تتخذ إجراءً ملزمًا، وأن يُفرّق بين التفعيل والاتصال، وألا يؤثر فشلها في الأساسي. ولا يوجد خادم نموذج معتمد بعد (Q-16).
- **القرار:**
  1. مشروع ومخطط مستقلان؛ لا وحدة أساسية تعتمد عليه، وهو لا يكتب إلا في `ai` (اختبار آلي على الشيفرة). الإنشاء من المسودة يتم بإجراء المستخدم عبر الواجهات الأساسية وصلاحياتها، ثم يُسجل «طُبّق منه».
  2. واجهة مزوّد واحدة بموصل متوافق مع OpenAI لأي خادم داخلي أو مزوّد معتمد، ومزوّد تجريبي بقواعد للاختبار فقط ممنوع في الإنتاج.
  3. كل استدعاء يمر بترتيب ثابت: المفتاح ← صلاحية السجل و`ai.use` ← الحدود ← جاهزية المزوّد ← التصنيف ← التقليل للمزوّد الخارجي ← الاستدعاء ← تحقق الخادم ← الحفظ مسودة؛ وكل خطوة في سجل تشغيل دون محتوى.
  4. تحقق الخادم من المخرج مستقل عن المزوّد: لا عبارة بلا مرجع مرسل، ولا اقتباس غير موجود في مصدره، ولا مكلف خارج الدليل، ولا تاريخ لم يرد نصه.
  5. البحث التقليدي خدمة أساسية (`ISearchService`) تعمل دون الوحدة، والبحث الذكي يفسر السؤال إلى مرشحات ثم يستخدمها؛ فالنتائج سجلات حقيقية ضمن الصلاحيات.
  6. التعطيل لا يحذف ولا يُرسل: الجاري يُحجز ولا يُعرض حتى إفراج صريح بعد إعادة التفعيل، ومهام التفريغ المنتظرة تُحجز ولا تُستأنف آليًا.
  7. مفتاح API في مخزن أسرار مشفر بمفتاح رئيسي من البيئة أو من البيئة نفسها، والمضيف من قائمة البيئة؛ فلا تستطيع الواجهة توجيه البيانات لمضيف غير معتمد.
- **البدائل:** أن تنشئ الوحدة القرارات والمهام عند القبول (التصميم الأولي في 10 §4) — رُفض لصالح ضمانة أقوى: لا مسار كتابة أساسي في الوحدة إطلاقًا؛ بحث دلالي بالمتجهات — مؤجل لعدم توفر نموذج تضمين معتمد؛ إرسال الكل مع إخفاء لاحق — رُفض لأنه يخالف سياسة التصنيف.
- **العواقب:** تشغيل مزوّد حقيقي = ضبط المضيف والمفتاح والنموذج دون تغيير الشيفرة؛ وجودة الصياغة تُقاس قبل الإطلاق على مجموعة تقييم عربية (Q-18).
