# 25 — دليل التشغيل: التثبيت، وقاعدة البيانات، والأسرار، والنسخ الاحتياطي، والإدارة، والتكاملات، وواجهة API

> **لمن:** مسؤول البنية التحتية، ومسؤول قاعدة البيانات، ومدير النظام.
> **الحالة:** معدّ للبيئة التجريبية المؤسسية. **لم يُنفَّذ هذا الدليل على خادم إنتاج** (24 §10). ما اختُبر فعليًا موسوم بـ ✅، وما لم يُختبر موسوم بـ ⚠️.

## 2. التثبيت والتشغيل

### 2.1 المتطلبات

| البند | التجربة المؤسسية | ملاحظة |
|---|---|---|
| الخادم | 4 vCPU، و16 ج.ب ذاكرة، و200 ج.ب تخزين SSD | اختبار الأداء على نواتين أظهر تشبع المعالج تحت الحمل المتزامن (24 §6) |
| النظام | Linux (Ubuntu 22.04/24.04 أو RHEL 9) مع Docker Engine وCompose v2 | — |
| الشبكة | اسم نطاق داخلي (مثل majalis.jsdo.gov.sa)، وشهادة TLS، وفتح 443 للمستخدمين فقط | — |
| الوصول الصادر | إلى login.microsoftonline.com وgraph.microsoft.com عند ربط Entra، وخادم SMTP، ومزوّد الذكاء الاصطناعي الداخلي إن فُعّل | لا شيء آخر مطلوب |
| موقع خارجي للنسخ | خادم أو تخزين خارج الخادم الأساسي (Q-24) | إلزامي قبل التجربة ببيانات حقيقية |

### 2.2 بناء الصورة

تُبنى في بيئة متصلة (خادم البناء أو خط التكامل المستمر)، ثم تُنقل إلى الخادم:

```bash
docker build -t ccms:0.1.0 .
docker save ccms:0.1.0 | gzip > ccms-0.1.0.tar.gz      # للنقل إلى خادم غير متصل
docker load < ccms-0.1.0.tar.gz                          # على الخادم
```

صورة الإنتاج تُبنى بمشغّل Npgsql (UseNpgsql=true في Dockerfile). التطبيق يرفض الإقلاع في الإنتاج بموصل التطوير المصغّر.

### 2.3 التثبيت لأول مرة

1. انسخ المستودع (أو حزمة الإصدار) إلى /opt/ccms.
2. **الشهادة:** ضع fullchain.pem وprivkey.pem في deploy/certs. وعدّل server_name في deploy/nginx/ccms.conf.
3. **المتغيرات:** انسخ deploy/.env.example إلى /opt/ccms/.env، واضبط الصلاحية 600، ثم املأ القيم (§7).
4. **قاعدة البيانات:**

   ```bash
   docker compose up -d db
   docker compose exec db psql -U postgres -v owner_pw="$CCMS_OWNER_PASSWORD" -v app_pw="$CCMS_APP_PASSWORD" -v db=ccms -f /bootstrap.sql
   ```

5. **الترحيلات:** تُطبق بحساب المالك، وتنتهي الحاوية:

   ```bash
   docker compose run --rm migrate
   ```

6. **التشغيل:**

   ```bash
   docker compose up -d app nginx
   docker compose ps          # app يجب أن يكون healthy
   ```

7. **أول مدير:** بحساب طوارئ محلي مؤقت إلى أن يُربط Entra:

   ```bash
   docker compose run --rm app bootstrap-admin --email admin@jsdo.gov.sa --name "مدير النظام" --password '<كلمة مؤقتة قوية>'
   ```

   - يتطلب الدخول المحلي LOCAL_LOGIN_ENABLED=true مؤقتًا. BreakGlassOnly مفروض في الإنتاج.
   - غيّر كلمة المرور فور الدخول.
   - بعد ربط Entra، أعد LOCAL_LOGIN_ENABLED=false.
8. **التحقق:**
   - افتح https://<النطاق>/.
   - تحقق من /health/ready، وشاشة «التكاملات»، و«إعدادات النظام».

**إذا رفض التطبيق الإقلاع:** في الإنتاج يرفض الإقلاع بإعدادات ضعيفة، ويطبع قائمة الأسباب في سجل الحاوية (docker compose logs app). الأسباب:

- غياب Npgsql.
- AllowedHosts=«*».
- غياب DataProtection:KeysPath.
- مفتاح رئيسي بطول خاطئ.
- سر المزوّد التجريبي مضبوط.
- مسار تخزين نسبي.
- الترحيل عند الإقلاع.
- حساب التطبيق ccms_owner.

### 2.4 التشغيل اليومي والترقية

| العملية | الأمر |
|---|---|
| الحالة | docker compose ps، وcurl -k https://<النطاق>/health/ready |
| السجلات | docker compose logs --since 1h app (سجلات منظمة دون أسرار ولا قيم صفوف) |
| إعادة التشغيل | docker compose restart app (الجلسات تبقى صالحة لأن مفاتيح حماية البيانات في وحدة تخزين دائمة) |
| الترقية | خذ نسخة (§3)، ثم حمّل الصورة الجديدة واضبط CCMS_VERSION، ثم docker compose run --rm migrate، ثم docker compose up -d app |
| التراجع | الترحيلات أمامية فقط. التراجع بعد ترحيل يعني الاستعادة من النسخة السابقة للترقية (§4) |

## 3. النسخ الاحتياطي

### 3.1 ما يُنسخ

| المكوّن | الطريقة | لماذا |
|---|---|---|
| قاعدة البيانات | pg_dump بصيغة custom بحساب المالك | كل السجلات والإعدادات والتدقيق |
| مجلد المستندات (/var/lib/ccms/storage) | tar | الملفات المرفقة وإصدارات PDF الموقعة. القاعدة تحفظ بصماتها فقط |
| مفاتيح حماية البيانات (/var/lib/ccms/keys) | tar | من دونها تبطل الجلسات ورموز الحماية بعد الاستعادة |
| لقطة الإعدادات غير السرية | نسخ | للمطابقة عند الاستعادة |
| بيان | أعداد صفوف 13 جدولًا، ورأس سلسلة التدقيق، وSHA256SUMS | للتحقق بعد الاستعادة (§5) |

**لا تُنسخ ضمن الأرشيف:** الأسرار (ملف .env وعبارة مرور النسخ). تُحفظ في خزنة المكتب منفصلة (§7).

### 3.2 الحماية والدورية والاحتفاظ

- **التشفير:** openssl enc -aes-256-cbc -pbkdf2 -iter 200000 بعبارة مرور من ملف (BACKUP_PASSPHRASE_FILE، صلاحية 600).
- **حماية السلامة:** ملف sha256 للأرشيف كله. التعديل يُكتشف قبل فك التشفير.
- **الدورية المقترحة:** نسخة كاملة يومية الساعة 01:30 (ccms-backup.timer)، وتشغيل يدوي قبل كل ترقية.
- **الاحتفاظ:** 14 يومية، و8 أسبوعية (نسخة الأحد)، و12 شهرية (نسخة أول الشهر). يُضبط بـ KEEP_DAILY وKEEP_WEEKLY وKEEP_MONTHLY.
- **خارج الموقع:** بعد كل نسخة ناجحة تُنسخ إلى موقع خارج الخادم (ExecStartPost في ccms-backup.service). الموقع يحدده المكتب (Q-24).

**التفعيل على المضيف:**

```bash
sudo install -m 600 /dev/null /etc/ccms/backup.pass && openssl rand -base64 48 | sudo tee /etc/ccms/backup.pass >/dev/null
sudo cp deploy/backup/ccms-backup.{service,timer} /etc/systemd/system/
sudo systemctl daemon-reload && sudo systemctl enable --now ccms-backup.timer
sudo systemctl start ccms-backup.service && journalctl -u ccms-backup -n 50      # أول نسخة يدويًا
```

### 3.3 أهداف الاستعادة (بانتظار اعتماد المكتب — Q-24)

| الهدف | المقترح | الأساس |
|---|---|---|
| RPO (أقصى فقد بيانات مقبول) | 24 ساعة بالنسخ اليومي في التجربة. **4 ساعات أو أقل في الإنتاج** بأرشفة WAL المستمرة (NFR-AVL-02) | النسخ اليومي وحده يفقد عمل يوم كامل |
| RTO (أقصى زمن استعادة) | 4 ساعات | الاستعادة المختبرة لقاعدة 1.6 م.ب استغرقت دقائق. قاعدة سنوات من النشاط (تقدير بضعة ج.ب) تُستعاد خلال أقل من ساعة، والباقي للتحقق والتشغيل |

**هذه الأهداف مقترحات فنية وليست معتمدة.** تُعتمد من المكتب، ثم تُعاد صياغة الدورية وفقها.

## 4. الاستعادة

**القاعدة:** لا تكتب أبدًا فوق القاعدة العاملة. السكربت يرفض قاعدة قائمة أو مجلد تخزين غير فارغ.

1. **أوقف التطبيق** إن كانت الاستعادة بديلًا للإنتاج: docker compose stop app.
2. **استعد إلى قاعدة ومجلد جديدين:**

   ```bash
   # ccms-restore.sh <الأرشيف> <القاعدة الجديدة> <مجلد المستندات الجديد> [مجلد المفاتيح الجديد]
   BACKUP_PASSPHRASE_FILE=/etc/ccms/backup.pass PGHOST=... PGUSER=postgres PGPASSWORD=... \
   deploy/backup/ccms-restore.sh /var/backups/ccms/daily/ccms-<STAMP>.tar.enc \
     ccms_restore_20261018 /var/lib/ccms/storage-restore /var/lib/ccms/keys-restore
   ```

   السكربت ينفذ بالترتيب:
   - يتحقق من بصمة الأرشيف.
   - يفك التشفير.
   - يتحقق من SHA256SUMS.
   - ينشئ القاعدة بمالكها ccms_owner.
   - يستعيد بـ pg_restore.
   - يستعيد المستندات والمفاتيح.
3. **تحقق** (§5). لا تنتقل إلى الخطوة التالية قبل نجاحه.
4. **حوّل التطبيق** إلى القاعدة والمجلد المستعادين:
   - اسم القاعدة في ConnectionStrings.
   - ربط وحدتي التخزين.
   
   ثم شغّله، وراجع /health/ready.
5. **وثّق الاستعادة:** السبب، والنسخة، والزمن الفعلي، ونتيجة التحقق.

## 5. التحقق من الاستعادة واختباراتها

«وجود ملف النسخة ليس دليلًا على إمكانية الاستعادة». بعد كل استعادة:

```bash
# ccms-restore-verify.sh <القاعدة المستعادة> <مجلد المستندات المستعاد> <مجلد بيانات الاستعادة> [مسار الترحيلات]
CCMS_HOST_DLL=/app/Ccms.Host.dll CCMS_APP_CS="Host=...;Database=ccms_restore_20261018;Username=ccms_app;Password=..." \
deploy/backup/ccms-restore-verify.sh ccms_restore_20261018 /var/lib/ccms/storage-restore /var/lib/ccms/storage-restore.restore-meta db/migrations
```

**ما يتحقق منه:**

1. أعداد الصفوف تطابق البيان.
2. سلسلة التدقيق سليمة، ورأسها يطابق المحفوظ.
3. كل مستند غير متلف موجود وبصمته مطابقة. الملفات اليتيمة تُعدّ للعلم.
4. عدد الترحيلات المطبقة يساوي ملفات الترحيل.
5. المفاتيح والأسرار المخزنة موجودة.
6. اختياريًا: يشغّل التطبيق على القاعدة المستعادة، ويطلب /health/ready و/api/v1/system/info.

**تمرين الاستعادة الدوري:**

- **ربع سنوي:** استعادة أحدث نسخة على خادم منفصل والتحقق منها (NFR-AVL-03).
- **نصف سنوي:** تمرين كامل بزمن مقيس مقابل RTO.
- **النتيجة:** تُسجل في سجل التمارين.

**ما نُفذ فعليًا:**

- استعادة كاملة في بيئة منفصلة على خادم التطوير، مع حالاتها السلبية.
- الدليل في docs/test-results/backup-restore.md.

**ما لم يُنفذ:** الاستعادة على خادم مختلف، والنسخ خارج الموقع.

## 6. إعداد قاعدة البيانات

| البند | القيمة |
|---|---|
| الإصدار | PostgreSQL 16 (المختبر). 13 فما بعد مطلوب لامتداد pg_trgm الموثوق |
| الترميز | UTF8، من template0 |
| الأدوار | ccms_owner يملك المخططات وتُشغَّل به الترحيلات فقط. ccms_app لوقت التشغيل، بلا DDL، وبلا UPDATE أو DELETE على سجلات التدقيق والإصدارات والتوقيعات (يفرضها الترحيل) |
| الامتدادات | pg_trgm (V014، لفهارس البحث). ينشئه مالك القاعدة دون صلاحية مدير |
| الترحيلات | db/migrations/V001..V014، تُطبق بأمر migrate بالترتيب. كل ترحيل مسجل ببصمته، فأي تعديل على ترحيل مطبق يوقف الأمر |
| الاتصال | ConnectionStrings:App بحساب ccms_app، وConnectionStrings:Migrations بحساب ccms_owner (في حاوية الترحيل فقط) |
| الشبكة | قاعدة البيانات على الشبكة الداخلية لـ Compose فقط، بلا منفذ معروض |

**الإعداد اليدوي (خارج Compose):**

```bash
psql -h <db-host> -U postgres -v owner_pw='...' -v app_pw='...' -v db=ccms -f db/bootstrap.sql
ConnectionStrings__Migrations="Host=<db-host>;Database=ccms;Username=ccms_owner;Password=..." dotnet Ccms.Host.dll migrate
```

**ضبط مقترح للتجربة:**

- shared_buffers = 25٪ من الذاكرة.
- effective_cache_size = 50–75٪ من الذاكرة.
- random_page_cost = 1.1 على SSD.
- log_min_duration_statement = 500ms لرصد البطء.

**الإنتاج:** أرشفة WAL مستمرة إلى موقع منفصل لتحقيق RPO أقل من يوم، ونسخة متماثلة للقراءة عند الحاجة (NFR-AVL-02).

## 7. إدارة الأسرار

| السر | مكانه | التوليد | التدوير |
|---|---|---|---|
| كلمة مدير PostgreSQL | .env (PG_SUPERUSER_PASSWORD) | openssl rand -base64 32 | سنويًا أو عند مغادرة مسؤول |
| كلمتا ccms_owner وccms_app | .env | openssl rand -base64 32 | سنويًا: ALTER ROLE ثم تحديث .env ثم إعادة التشغيل |
| المفتاح الرئيسي لمخزن الأسرار (CCMS_SECRETS_MASTER_KEY) | .env | openssl rand -base64 32 (32 بايت بالضبط) | **لا يُغيَّر دون إعادة تشفير الأسرار المخزنة.** فقده يعني إعادة إدخال أسرار التكاملات |
| سر تطبيق Entra (ENTRA_CLIENT_SECRET) | .env | من بوابة Entra | قبل انتهائه (تنبيه في التقويم) |
| أسرار التكاملات (GRAPH_CLIENT_SECRET، SMTP_PASSWORD، مفتاح المراسلات، مفتاح الذكاء الاصطناعي) | مخزن الأسرار في النظام (AES-256-GCM بالمفتاح الرئيسي)، أو متغير بيئة Secrets__Values__NAME | من المزوّد | من شاشة الإعدادات. القيمة لا تُعرض بعد الحفظ |
| مفاتيح حماية البيانات | وحدة التخزين keys (ينشئها التطبيق ويدورها آليًا) | آلي | آلي. تُنسخ احتياطيًا |
| عبارة مرور النسخ | /etc/ccms/backup.pass (600) | openssl rand -base64 48 | سنويًا. النسخ القديمة تبقى بعبارتها القديمة، فتُحفظ كل العبارات |
| شهادة TLS | deploy/certs | من جهة الإصدار المعتمدة | قبل الانتهاء |

**قواعد:**

1. لا أسرار في المستودع ولا في الصورة. ملف .env مستثنى في .gitignore.
2. نسخة من .env وعبارات النسخ في **خزنة المكتب** (مظروف مختوم أو مدير أسرار)، بمسؤولين اثنين على الأقل.
3. التطبيق لا يعيد أي سر في استجابة، ولا يكتبه في سجل (P8-13).
4. عند الاشتباه بتسرب: دوّر السر، وراجع سجل التدقيق وسجل الموصلات لفترة الاشتباه.

| سجل التدقيق | «التقارير»، تبويب التدقيق | **للمدقق فقط**، لا لمدير النظام (فصل المهام). فحص سلامة السلسلة: GET /api/v1/audit/integrity |

**المراقبة:**

- /health/live: العملية تعمل.
- /health/ready: القاعدة متاحة.
- تنبيه عند فشل النسخة اليومية (journalctl -u ccms-backup).
- تنبيه عند امتلاء التخزين فوق 80٪.
- مراقبة قائمة البريد المعلق في «التكاملات».

**استكشاف الأخطاء:**

| العرض | السبب المحتمل | الإجراء |
|---|---|---|
| 400 «Bad Request - Invalid Hostname» | اسم النطاق ليس في AllowedHosts | صحح CCMS_HOSTNAME |
| عنوان المنفذ في التدقيق هو عنوان nginx | الوكيل ليس في Network:TrustedProxies | طابق عنوان nginx في Compose |
| تسجيل خروج الجميع بعد إعادة التشغيل | وحدة keys غير دائمة | تحقق من ربط keys |
| 429 Too Many Requests | تجاوز حد الطلبات (600/دقيقة للمستخدم، 30 تصديرًا/دقيقة، 10 محاولات دخول/دقيقة للعنوان) | اضبط RateLimits:* إن كان الاستخدام مشروعًا |
| رسائل بريد معلقة | خادم SMTP غير متاح | الصادر يعيد المحاولة بتباعد. افحص الاتصال من «التكاملات» |

## 9. التكاملات ومتطلباتها

**لا يوجد تكامل متصل فعليًا حتى الآن.** كل الموصلات منفذة ومختبرة مع خوادم وهمية، وتعرض «غير مهيأ» حتى ينجح فحص الاتصال (23 §4).

| التكامل | المفتاح | ما يلزم من المكتب | الحالة |
|---|---|---|---|
| الدخول الموحد (Entra ID، OIDC) | SSO_ENABLED | تسجيل تطبيق دخول، ومعرّف المستأجر والتطبيق والسر، وعنوان الرجوع https://<النطاق>/auth/sso/callback، ونطاقات البريد المسموحة | مختبر بمزوّد هوية وهمي (RST-04/05) — Q-21 |
| مزامنة الدليل | DIRECTORY_SYNC_ENABLED | تطبيق تكامل بدور User.Read.All بموافقة المسؤول | مختبر بخادم وهمي — Q-21 |
| البريد | EMAIL_INTEGRATION_ENABLED | خادم SMTP داخلي، وحساب إرسال، وعنوان المرسل، والسماح من عنوان الخادم | مختبر بخادم SMTP وهمي — Q-04 |
| الاجتماعات المرئية (Teams) | VIDEO_MEETINGS_ENABLED | دور OnlineMeetings.ReadWrite.All، وسياسة وصول تطبيقي، ومستخدم منظِّم | مختبر بخادم وهمي — Q-21 |
| مستودع الوثائق (SharePoint) | DOCUMENT_REPOSITORY_ENABLED | مكتبة مخصصة، ومعرّف Drive، وSites.Selected | مختبر بخادم وهمي (رفع حتى 4 م.ب) — Q-22 |
| نظام المراسلات | CORRESPONDENCE_INTEGRATION_ENABLED | توثيق واجهة المورد، أو اعتماد عقد ccms-letters-v1 | محوّل لعقد مقترح — Q-07، Q-23 |
| التوقيع الإلكتروني | E_SIGNATURE_ENABLED | مزوّد معتمد وعقد وواجهة. حتى ذلك: الموافقة الموثقة داخل النظام | Q-09 |
| الذكاء الاصطناعي | AI_ENABLED | استضافة نموذج داخلي أو معتمد، وموافقة الأمن السيبراني، وحد التصنيف | مزوّد تجريبي فقط — Q-16 |
| فحص البرمجيات الضارة | — | حل معتمد (ClamAV أو غيره) | غير منفذ — Q-15 |

**خطوات تفعيل أي تكامل:**

1. اضبط الإعدادات في بيئة الخادم، والسر في مخزن الأسرار.
2. نفّذ «فحص الاتصال» من «التكاملات».
3. فعّل المفتاح من «إعدادات النظام» بسبب مكتوب.
4. راقب سجل الاستدعاءات أول أسبوع.

## 10. توثيق واجهة API

| البند | التفاصيل |
|---|---|
| الوصف الآلي | docs/api/openapi-v1.json (OpenAPI 3، 234 مسارًا و261 عملية، مصدّر من النظام في هذه المرحلة) |
| الوصف الحي | /openapi/v1.json وواجهة /swagger في بيئتي التطوير والاختبار. معطل في الإنتاج (OpenApi:Enabled=false) |
| العقد والاصطلاحات | 11، وفهرس نقاط النهاية حسب الوحدة في 11 §2 |
| الأساس | /api/v1. JSON بأسماء camelCase. التواريخ ISO 8601 UTC |
| المصادقة | كعكة جلسة HttpOnly (ccms.session) من الدخول المحلي أو الموحد. لا رموز Bearer للمستخدمين |
| CSRF | كل طلب غير GET يحمل ترويسة X-CSRF-Token من GET /api/v1/auth/csrf |
| الأخطاء | Problem Details (RFC 9457) برمز مشكلة ثابت (code)، مثل not-found وfeature-disabled وnot-a-signer. لا تفاصيل داخلية ولا تتبع |
| الحدود | 600 طلب/دقيقة للمستخدم، و30 تصديرًا/دقيقة، و10 محاولات دخول/دقيقة للعنوان. الرد 429 |
| الصلاحيات | تُفحص في الخادم لكل طلب. ما خارج نطاق المستخدم يعطي 404. الإجراء غير المسموح يعطي 403 |

**مثال:**

```bash
curl -c j -b j https://<النطاق>/api/v1/auth/csrf                           # {"token":"..."}
curl -c j -b j -H "X-CSRF-Token: <token>" -H "Content-Type: application/json" \
     -d '{"email":"...","password":"..."}' https://<النطاق>/api/v1/auth/login
curl -b j "https://<النطاق>/api/v1/tasks?overdue=true&pageSize=50"
```

## 11. بيئة التجربة على GitHub Codespaces

**الغرض:** تجربة النظام ومشاركته ببيانات وهمية قبل خادم المكتب. التعليمات خطوة بخطوة في deploy/trial/README.md.

**المكوّنات:**

| الملف | الدور |
|---|---|
| .devcontainer/devcontainer.json | المساحة: Docker داخل المساحة، و.NET 10 للتحقق، وإعادة توجيه المنفذ 8080 |
| deploy/trial/setup.sh | ينفذ بالترتيب: توليد الأسرار، وبناء صورة الإنتاج، والقاعدة، والترحيلات، والبيانات الوهمية، والتشغيل، وفحص الدخان |
| deploy/trial/start.sh | إعادة التشغيل عند استئناف المساحة |
| deploy/trial/docker-compose.trial.yml | تجاوز ملف النشر: بيئة Trial، والمنفذ 8080 على localhost، ودون nginx |
| deploy/trial/smoke.sh | فحص دخان من 35 تحققًا عبر الواجهة البرمجية الحقيقية |
| deploy/trial/verify-npgsql.sh | الاختبارات الـ142 بمشغّل Npgsql على قاعدة مؤقتة |
| appsettings.Trial.json | إعدادات بيئة Trial |

**بيئة Trial:** تُطبق ضوابط إقلاع الإنتاج كلها (25 §2.3)، عدا ثلاثة استثناءات:

1. الدخول المحلي لكل الحسابات، فلا دخول موحد في التجربة.
2. المزوّدان التجريبيان للتوقيع والذكاء الاصطناعي مسموحان. سر المزوّد التجريبي إلزامي بطول 32 حرفًا على الأقل.
3. أمر seed-sample مسموح بشرط --password بكلمة مولدة لا تقل عن 14 حرفًا. الكلمة المنشورة في المستودع مرفوضة.

**ما بقي على حاله:**

- الإنتاج ما زال يرفض الاستثناءات الثلاثة.
- seed-sample ما زال ممنوعًا في الإنتاج.
- الواجهة تعرض في الترويسة وصفحة الدخول تنبيهًا أحمر: «بيئة تجربة — بيانات وهمية فقط».

**ما تحقق محليًا قبل التسليم:**

| التحقق | النتيجة |
|---|---|
| قواعد seed-sample | بلا كلمة: رُفض. الكلمة المنشورة: رُفضت. الكلمة المولدة: نجح، وإعادة التشغيل لا تكرر. الإنتاج: رُفض |
| الإقلاع في Trial بإعدادات Compose | السبب الوحيد للرفض غياب Npgsql (متوقع بموصل التطوير) |
| الإعدادات الضعيفة في Trial | AllowedHosts=«*» والسر القصير رُفضا |
| الإنتاج بالإعدادات نفسها | رفض الدخول المحلي العام والسر التجريبي |
| فحص الدخان على خادم التطوير مع تصفية المضيف | 33/35. الفاشلان خاصان ببيئة التطوير (اسم البيئة والكلمة المنشورة)، وينجحان في Trial بالتصميم |
| دمج ملفي Compose | صحيح (docker compose config) |

**ما لم يُختبر:** الإنشاء الفعلي في Codespaces، وبناء الصورة، وتشغيل verify-npgsql.sh. هذه أول تجربة لمشغّل Npgsql (R-22)، فإن ظهر فيها خلل فهو متوقع الاكتشاف هنا، لا في الإنتاج.
